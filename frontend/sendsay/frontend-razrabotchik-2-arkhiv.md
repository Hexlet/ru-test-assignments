## Форма авторизации

Вам нужно реализовать возможность логина под своим собственным логином/саблогином/паролем.

Обязательные поля:

* Логин
* Пароль
Нельзя сабмитить формы с незаполнеными обязательными полями, при попытке нужно подсветить невалидные поля.

Логином может быть как email, так и строка из латинских букв, цифр и подчеркиваний.

В пароле пробелы могут встречаться, а кириллица — нет, поэтому подойдите к правилам валидации осмысленно.

При неуспешной попытке входа нужно показать сообщение о том, что «Вход не вышел», и ошибку, которую вернул сервер — в качестве описания.

Авторизация сохраняется при перезагрузке страницы — это сделать не сложно.

### Интерфейс консоли

Консоль состоит из набора панелей, которые занимают всё свободное пространство окна:

* Заголовка
* Полей запроса-ответа
* Истории запросов
* Панели с действиям
Панели занимают всю ширину и высоту окна — растягиваются и сжимаются поля запроса и ответа. Минимальный размер 640х520, после появляются полосы прокрутки.

#### Заголовок

Заголовок показывает `account` и `sublogin` из ответа «понга». Если авторизовывались без саблогина, `sublogin` показывать не нужно.

```plain text
REQUEST:
{
  "action":"pong"
}

RESPONSE:
{
  "request.id": "...",
  "sublogin": "codeception",
  "ping": 1590062030,
  "account": "codeception",
  "duration": 0.012925,
  "_ehid": "215521.996867202571.1590062030"
}
(У вас может быть немного другим набор полей, т.к. у автора заданий видоизменный api-client)
```

Кнопка «Выйти» должна делать логаут и переносить пользователя на форму авторизации.

Кнопка перехода в полноэкранный режим (см. пояснения к макету) — разворачивает окно «на все деньги», подобно YouTube или Vimeo.

#### Поля запроса-ответа

Горизонтальный размер полей можно регулировать (см. пояснения к макету).

Размеры (пропорции) сохраняются при закрытии браузера.

Поле ответа не редактируется.

Вы можете использовать ваш любимый редактор кода с подсветкой синтаксиса для полей ввода и вывода, если хотите. Если не хотите, то можно традиционное поле для ввода, но с моноширинным шрифтом.

#### Отправка запросов к серверу

Запрос к серверу — это валидный JSON. Если в поле ввода невалидно, то нужно подсветить поле ввода.

* Парочка валидных запросов для теста
Если поле ввода запроса валидно, то нужно:

* отправить запрос и показать ответ сервера
* если запрос уникальный, то добавить в историю запросов элемент
    * если запрос не уникальный, то в истории запросов передвинуть его элемент в начало
Отправка запросов происходит по нажатию кнопки «Отправить» (ну так, на всякий случай). При нажатии «Форматировать» нужно отформатировать текст запроса:

```plain text
Было—стало

{    "action":  "pong"}

↓

{
    "action": "pong"
}
```

#### История запросов

Приложение умеет хранить до 15 последних уникальных валидных запросов и умеет отображать их в обратном хронологическом порядке — это когда последний выполненный стоит первым в списке.

Если запрос валиден (с точки зрения валидатора JSON), но при выполнении произошла ошибка, то запрос сохраняется в истории, но так же сохраняется информация об ошибке.

При закрытии вкладки браузера история не должна пропадать.

Список элементов истории запросов умеет прокручиваться горизонтально с помощью колеса мыши. Полосу прокрутки лучше не показывать.

#### Элемент истории запросов

Элемент истории умеет:

* Показывать статус выполнения запроса — без ошибок отмечаются зеленым цветом, с ошибками — красным
* Выводить значение свойства `action` из запроса, например `track.get`
* При нажатии на элемент, подставлять в поле ввода запроса *отформатированный* сохраненный запрос
*Кроме этого, мы хотим посмотреть, как вы справитесь с созданием сложного составного компонента, поэтому элемент истории содержит в себе «дропдаун» (см. пояснения к макету).*

Дропдаун элемента истории запросов содержит действия:

* Выполнить — в поле запроса вставляется сохраненный запрос и выполняется (без физического нажатия кнопки «отправить»)
* Скопировать — запрос копируется в буфер обмена, и показывается визуальный отклик этого действия (см. пояснения к макету)
* Удалить — безвозвратно удаляет запрос из истории запросов, без диалоговых окон. Если хотите добавить «тост» с действием отмены, то мы не против.

### 🤔 Наши ожидания

> **Эта вакансия на regular-разработчика, а не на junior.
**Ожидаем от вас полноценные знания javascript и react, на собеседовании будем задавать вопросы. Мы не против доучивать junior-разработчиков, но для них есть другая вакансия.

Сначала мы будем смотреть, работает задание или нет, поэтому **нам нужна ссылка с работающим заданием**. Мы не хотели бы клонировать ваш репозиторий, чтобы его проверить, — нас устроит работающая версия, размещенная на вашем любимом хостинге, и код в публичном репозитории на GitHub с открытым пулл-реквестом.

Мы будем проверять работоспособность ваших тестовых в последней версии Chrome, но можем и в Firefox посмотреть и в Safari — в IE, Edge и древних операх смотреть никто (из нас) не будет.

Мы будем оценивать работоспособность приложения, подход к заданию, качество и структуру кода, подход к верстке макетов, внимательность и, возможно, умение задавать вопросы.

Мы ожидаем, что в этом SPA вы:

* будете использовать React и Redux
* напишете его используя JS ES6 — ***просьба не использовать TypeScript***
* опишете стили по БЭМ или SUIT CSS
* используете библиотеку-коннектор для нашего API [https://github.com/sendsay-ru/sendsay-api-js](https://github.com/sendsay-ru/sendsay-api-js) — *она работает, см. README.MD*
* сделаете валидацию полей и объясните, почему решили сделать именно такую валидацию
* оптимизируете рендер
* оптимизируете графику
> **НЕ ИСПОЛЬЗУЙТЕ CSS-in-JS решения
**Если используете LESS, SASS, Stylus — напишите для каких целей вы используете в этом проекте.

Мы хотели бы, чтобы вы посмотрели продукт, имели представление о нем и поработали с описанием Sendsay API.

### 🚑 Служба моральной поддержки

Скорее всего мы неидеально написали тестовое задание, и вы поможете нам его уточнить, если зададите вопросы. Видите какую-то непреодолимую сложность — *не играйте в телепатов и экстрасенсов, задайте вопрос.*

### ☎️ Мы вам перезвоним

Мы смотрим, проверяем код и тестируем функциональность всех тестовых заданий. На проверку тестового задания, сделанного на среднем уровне (не совсем плохо, но и не восхитительно) уходит от двух дней до недели.

Восхитительно сделавшим тестовое мы почти не пишем комменты и сразу зовём пообщаться. Сделавшим «совсем плохо» тоже стараемся отвечать побыстрее, но иногда пишем общими фразами.

Иногда мы просим доработать какие-нибудь части задания — так мы проверяем, насколько комфортно нам будет вместе работать.
